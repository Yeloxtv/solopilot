# Specification: having the client approve the scope

Status: agreed on 2026-10-11, done. Workstream 2 of the [roadmap](../roadmap.md).

## Goal

The quote buys "the app", not a list of features. solopilot draws from the plan a scope document the client approves in writing. The approval is recorded, and becomes the reference any request to add something is then measured against.

## The scope document

Generated from `solopilot.yaml`, in the project's language, with no delay, margin or internal projected date. It holds:

| Section | What it takes from the plan |
| --- | --- |
| The goal | `goal` and the target date |
| Guaranteed for the date | The core features, by area, each with its source in the spec |
| Planned next, within the budget | The other features of the plan |
| Not planned at this stage | What is below the line: possible only if time remains, with no commitment |
| Out of scope | The exclusions (`scope: out`), with the reason |
| What we need from you | The dependencies: who, what, and around which planned date it is needed |
| Questions to settle | The open questions: who answers, what it unblocks, by which planned date. Those the developer must answer themselves stay out |
| Pending requests | The requests not yet triaged, to be estimated separately |
| Agreement | Name, date, signature, or a simple "approved" by email |

Citing the source of each feature shows the client that their spec is covered point by point, and what was not in it.

## The flow

1. The plan is agreed internally: `solopilot baseline`, as today.
2. `solopilot scope` generates the document. The skill proposes the cover message.
3. The client answers. If they ask for changes, it is a replan (mode 4 of the skill), then a new document.
4. When they approve, `solopilot scope --agreed-by "Name" --on YYYY-MM-DD` records the approval.

The plan agreed internally lets development start without waiting for the client. The client's approval, for its part, becomes the reference for the scope.

## Changes to the tool

- `solopilot scope` writes `build/scope.html`, a clean page made to be printed as PDF, and `build/scope.md`, the same content as text, to paste into an email.
- `solopilot scope --agreed-by <name> [--on <date>]` writes `project.scope_agreed: { by, date }`, adds an `agreed` entry to the log, commits and sets the git tag `scope-agreed-<date>` in the pilot directory. The tagged file keeps the exact state of the approved scope: the growth of the scope (workstream 4) will be measured against it.
- The dashboard mentions the approval: "Scope approved by Ms Le Goff on October 20".
- At step 6 of the first plan, the skill runs `baseline` then `scope`, and proposes the message to the client. When the developer reports the client's approval, it records it.

## Decisions (2026-10-11)

1. **The form of the document.** *Recommended: a page to print as PDF and text for the email, generated by the command line.* The content is the same every time, and nothing internal can slip into it. The alternatives: a page published on claude.ai, which the client may not be able to open, or a text written by Claude each time, less reliable.
2. **When the approval comes.** *Recommended: the plan agreed internally first, the client's approval afterwards, recorded separately.* The alternative is to wait for the client's approval to close planning, which would hold up the start.
3. **What is authoritative.** *Recommended: the client's approval becomes the reference for the scope as soon as it exists, the plan agreed internally otherwise.*
4. **The content.** *Recommended: the nine sections above, sources included.*

## Decisions (2026-10-12), after a first reread of the document

5. **The dates are the plan's, not the work's.** The dashboard dates an answer from where the work stands; a document regenerated while the project runs late would then show every date slipping, and a client comparing two versions would read the delay. The document dates each answer from day 1 at the plan estimate, as if no work had been done: the dates move only when the plan changes.
6. **The owner's own questions stay out.** A question the developer must answer themselves (`who` is `project.owner`) is not the client's business.
7. **A request as a source reads "requested by".** A feature added by a request keeps `source: R01` in the plan; the document shows "requested by Harbor & Pine" instead of the id.

## How it is tested

- Unit tests: the document holds no margin, no delay and no projected date; each category takes the right features; the approval writes `scope_agreed`, the log entry and the tag.
- End-to-end scenario: at the end of Kerlan's planning, the skill generates the document and proposes the message; then "the client approved, it's Ms Le Goff, on October 20" records the approval.
